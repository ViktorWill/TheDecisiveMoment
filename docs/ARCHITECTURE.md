# Architecture

## What the app is

A field companion for street photography. Three sections — a spot **Map**, a **Light** advisor,
and a **Community** section that is modelled now and served later.

Two properties drive nearly every decision below:

1. **It is used outdoors, abroad, on bad or expensive data.** Offline is the default state, not a
   degraded mode.
2. **The camera is a manual rangefinder.** There is no autofocus and no auto-exposure to fall back
   on, so the app's numeric output has to be good enough to dial in without second-guessing.

## Constraints and decisions

| Decision | Choice | Why |
|---|---|---|
| Language / UI | Swift 6, SwiftUI, iOS 18+ | Single-platform, single-user-class app. Strict concurrency from day one is cheaper than retrofitting it. |
| Project file | Generated by XcodeGen from `project.yml` | Keeps the whole project text-based and reviewable. An agent can restructure targets with an ordinary edit instead of hand-patching `.pbxproj`. |
| Spot data | Static per-city JSON bundles on a CDN | No backend to run, pay for, or keep up. Bundle refreshes arrive as reviewable PR diffs. |
| CDN | GitHub Pages from this repo | Free, versioned, already where the code lives. |
| Weather | Apple WeatherKit | Native, no API key in the binary, 500k calls/month included with the developer membership already needed for TestFlight. |
| Sun position | Computed on device | The NOAA algorithm is ~80 lines. A network round-trip for something deterministic would be absurd, and it must work in airplane mode. |
| Persistence | SwiftData | First-party, fits the object graph, no dependency. Bundles are stored as decoded rows, not blobs, so map queries are indexable. |
| Community backend | Deferred behind a protocol | Standing up auth and moderation before the app is worth opening is the wrong order. |

```
                    ┌──────────────┐

                    └──┬────┬────┬─┘
             ┌─────────┘    │    └─────────┐
    ┌────────▼──────┐ ┌─────▼──────┐ ┌─────▼─────────┐
    │ TDMPersistence│ │ TDMWeather │ │   TDMSpots    │
    │  (SwiftData)  │ │(WeatherKit)│ │ decode/rank   │
    └────────┬──────┘ └─────┬──────┘ └─────┬─────────┘
             │              │              │
             │        ┌─────▼──────┐       │

             │        └─────┬──────┘       │
             └──────────────┼──────────────┘

                     │   TDMCore    │  value types, no framework imports
                     └──────▲───────┘
                            │
                   ┌────────┴────────┐

                   └─────────────────┘
```

### The rule that makes this worth doing

`TDMCore`, `TDMLight` and `TDMSpots` import **nothing from Apple's frameworks** — no Foundation
types beyond the cross-platform subset, no CoreLocation, no SwiftUI. They are plain Swift.

Three things follow:

- They build and test on Linux, so CI runs the entire logic suite in seconds on a free runner with
  no macOS minutes.
- They are trivially testable, because there is no simulator, no permissions dialog and no clock to
  stub — every function is inputs to outputs.
- `spotforge` links `TDMCore` directly, which means **the bundle-writing code and the
  bundle-reading code share one set of types.** The pipeline cannot emit a schema the app can't
  read; it would not compile.

Everything platform-bound is pushed to the edges: `TDMWeather` wraps WeatherKit behind a protocol,
`TDMPersistence` owns SwiftData, `TDMUI` owns SwiftUI. Those layers stay thin enough to verify by
reading.

### Module responsibilities

**`TDMCore`** — `Spot`, `SpotKind`, `SpotSource`, `City`, `CityIndex`, `GearProfile`, `CameraBody`,
`Lens`, `ShootSession`, `Photographer`, `Coordinate`. Value types, `Sendable`, `Codable`. No logic
beyond validation and derived properties.

**`TDMLight`** — solar position, the illuminance → EV model, the exposure solver, depth-of-field and
zone-focus maths, distance-scale snapping. Fully specified with test vectors in
[EXPOSURE-MODEL.md](EXPOSURE-MODEL.md). This is where the app's actual value lives.

**`TDMSpots`** — bundle decoding and integrity checking, the merge/dedupe/scoring rules, search and
filtering, and the `SpotStore` protocol the persistence layer implements. Ranking is here rather
than in the pipeline so a re-rank does not require a data rebuild.

**`TDMWeather`** — `WeatherProvider` protocol with `current(at:)` and `hourly(at:through:)`.
Implementations: `WeatherKitProvider`, and `StubWeatherProvider` for tests and previews. The
protocol exposes only what the light model consumes — cloud cover, condition, precipitation
intensity, visibility — so a second provider could be added later without touching callers.

**`TDMPersistence`** — SwiftData models for cached bundles, user pins, gear profiles and
calibration offsets. Owns the bundle download/verify/import flow.

**`TDMUI`** — views and the design system. Dark-first: this app gets used at dusk and at night, and
a white screen at blue hour ruins your night vision and your exposure judgement.

## Data flow

### Spots

```
  Overpass ─┐
  Wikidata ─┼─► spotforge ─► merge ─► score ─► bundles/v1/cities/{id}.json.gz
  Commons  ─┤   (build time)                             │
  curated  ─┘                                            ▼
                                              GitHub Pages (CDN)
                                                         │
                                       download once ────┤
                                                         ▼
   MapView ◄── TDMSpots (filter/rank) ◄── SwiftData ◄── verify sha256
                    ▲
                    └── user pins (local only in v1)
```

The app never calls Overpass or Commons at runtime. Overpass's usage policy is explicit that it is
not for client-side traffic, and doing the work at build time is also what makes the offline
guarantee real rather than aspirational.

### Light

```
  CoreLocation ─► coordinate ─┐
  system clock ─► timestamp  ─┼─► TDMLight.solarPosition ─► elevation, azimuth
                              │
  WeatherKit ─► cloud cover ──┼─► TDMLight.estimateEV ─► EV100 ± uncertainty
  user ──────► scene preset ──┘                              │
  user ──────► gear profile ─────────────────────────────────┼─► solve ─► f/N, shutter, ISO
  user ──────► strategy ─────────────────────────────────────┘            + zone focus range
                              ▲
  AVCaptureDevice ────────────┘  measured EV, calibration offset
```

Only the WeatherKit call touches the network, and its result is cached with a short TTL. With no
weather at all the model falls back to clear-sky and widens its stated uncertainty rather than
refusing to answer — a rough number in the field beats a spinner.

## Testing strategy

| Layer | How it is tested |
|---|---|
| `TDMLight` | Numeric test vectors in [EXPOSURE-MODEL.md](EXPOSURE-MODEL.md), verified against independent references (winter-solstice solar elevation, Sunny 16, published hyperfocal tables). Runs on Linux. |
| `TDMCore` / `TDMSpots` | Round-trip the example bundle in [DATA-BUNDLES.md](DATA-BUNDLES.md) as a committed fixture. Schema drift fails CI. Merge and scoring tested on synthetic clusters. |
| `spotforge` | Network sources behind a protocol; pipeline tested against recorded fixture responses, not live APIs. |
| `TDMWeather` | `StubWeatherProvider` only. The WeatherKit wrapper is thin enough to verify by inspection. |
| `TDMUI` | SwiftUI previews across light/dark and Dynamic Type. No snapshot tests — churn cost exceeds their value at this size. |

CI runs `swift test` on Linux for the three pure packages. A macOS job builds the app target.

## Privacy

Location never leaves the device. The only outbound calls are the WeatherKit request (Apple, coarse
coordinate) and the bundle download (a static file, identical for every user, revealing only which
city was fetched). No accounts, no analytics, no third-party SDKs in v1.

When the community section gains a backend, that changes materially and gets its own privacy review
before a line of it ships — see [SPEC-community.md](SPEC-community.md).
